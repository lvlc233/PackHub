# 产品画面与核心命题

> 这份是"我们在做什么"的总纲。其它文档各自解决一层，链接见文末。

## 一、核心命题

**整合 ≠ 堆叠。** 一个 Pack 的价值不在"装了多少东西"，而在"装完之后它们像一个整体一样工作"。

具体到可检查的判据，有四条：

1. **共享一套约定**：记忆写在哪、语气由谁定义、路径由谁发号施令——不能每个组件各有一套。
2. **可替换**：某个位置的实现不满意，换一个只改一行，其它部分不动。
3. **可验证**：不是"看起来能跑"，而是有可检查的证据（工具可见、入口被加载、状态可写）。
4. **可复现**：换一台机器、换一个人，装出来是同一套东西。

## 二、一个画面：Hub 上的创作流程

```
收藏（把见过的资源收进自己的池子）
  → 新建包（先写"要成为什么"，再选组件）
  → 选资源（从收藏里挑）
  → 调整（覆盖参数 / 改上游的默认值 / 统一路径）
  → 粘合（写 AGENTS.md、记忆 schema、脚本、loop —— 让它们成为一体）
  → 试跑（静态探针；有条件的跑一次场景）
  → 打包（.phub）→ 发布（可见性、签名、changelog）
```

Hub 是**创作台 + 仓库**：收藏、草稿、diff、探针结果、版本与发布都在它这里。它不执行——真正跑起来的是目标机器上的 runtime（见 [deployment.md](deployment.md)）。

## 三、「一生」只是一个比喻

我们讨论过一个极端例子：一个"像人一样"的整合包——会说话、能看懂、有记忆、会思考、有情感。

**它只是压力测试用例，不是要交付的产品。** 写在这里是因为它能逼出设计问题：

| 要的效果 | 落在哪一层 | 真正的难点不是"有"，而是"一致" |
|---|---|---|
| 说话 | TTS 工具 + 语气规则（粘合） | 语气由人格文件统一，不是每个组件各写一套 |
| 看懂 | 视觉能力要求 + 识图工具 | 看不懂时要承认，不能编 |
| 记忆 | 存储工具 + 记忆 schema + 状态目录 | 写什么、何时写、怎么检索，三件事要有约定 |
| 思考 | 推理/反思 skill | 触发点由粘合定义，不由清单编排 |
| 情感 | 状态文件 + 表达规则 | 情绪要跨会话延续，否则只是台词 |

从这个例子抽象出来的是**六层结构**，它对任何一个有追求的包都成立：

1. **形态声明**——要成为什么、需要什么环境能力（视觉？语音？长上下文？）。
2. **资源**——工具与 skill。
3. **内部改动**——覆盖上游默认值、改输出格式、换数据源。
4. **粘合**——AGENTS.md、记忆 schema、脚本、loop：不是组件，却决定组件能不能成一件事。
5. **状态**——需要持久化的目录与格式（默认不随包分发，包只带 schema 与种子）。
6. **验收**——静态探针 + 场景探针。

## 四、支撑"快速替换"的两个机制

### 1. 槽位与绑定（slots / bindings）

"这个 TTS 不行，换一个"必须是**一条命令**，不是重写清单。

```yaml
slots:
  voice:
    contract: [audio:speak]        # 占位实现必须提供什么
  memory:
    contract: [memory:read, memory:write]

resources:
  - { id: tts-a, type: tool, slot: voice, source: npm:tts-a@1.2.0 }
  - { id: tts-b, type: tool, slot: voice, source: "https://…/tts-b.tar.gz" }
  - { id: mem-file, type: mcp, slot: memory, source: npm:memory-server@0.9.0 }

bindings:
  voice: tts-b                     # 真正决定装哪个；换实现只改这一行
  memory: mem-file
```

- **候选留在清单里**，装不装由 `bindings` 决定；未绑定的候选不进入计划。
- **契约必须校验**：绑定的实现要覆盖 `slot.contract`，否则报错——否则“可替换”只是换个不通的东西。`packhub slot swap <slot> <id>` 一条命令换绑，并打印计划差异。
- 换绑时 `plan` 显示"卸掉谁、装上谁"，其它动作不变。

### 2. 路径统一（paths）

资源读取散乱，根源是每个上游各有默认落点。由包统一发号施令：

```yaml
paths:
  memory: .packhub/state/memory
  notes:  .packhub/state/notes
  glue:   .packhub/glue
```

资源里用 `${paths.memory}` 插值（写进 MCP 的 env、配置片段、overlay 的目标路径）。装进来的东西读同一个位置，不靠作者记谁的默认值是什么。

## 五、不在范围内（避免走偏）

- **不做某个具体的包**。「一生」是比喻，不是需求。
- **不在清单里写行为流程**（workflow）。顺序与策略在运行时；粘合是文件与状态，不是步骤声明。
- **不把"形态"做成必填字段**。它是作者的设计抽象，落在槽位集合上即可，Hub 可以据此渲染出"这个包有说话/记忆/视觉"。
- **不自建账号体系**、**不接管 agent 执行**、**不做运行时**。

## 六、怎么判断做对了

1. 换实现只改一行（`bindings`），`plan` 差异清楚。
2. 删掉上游资源仓库，包仍然装得上（vendored）或至少能明确报出缺什么。
3. 装完以后 agent 真的在用（工具可见、入口加载、状态可写），而不是"装上了但没生效"。
4. 别人照着包页能复现出同一套能力，`planHash` 一致。
