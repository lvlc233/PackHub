# PackHub 概念

### Pack（整合包）

一份可复用的 Agent 能力整合：不是把 Agent 需要的东西放在一起就够，而是这些功能能作为一个有机的整体给出。

Pack 不是资源的压缩包，哪怕有依赖关系也不自动成为有机整体；作为 Pack，需要创作者调整包内所有资源的关系，并以特定体验给出。

一个包内包括：

1. 清单 `packhub.yaml`
2. 锁 `packhub.lock.json`
3. 随包资源与补丁文件
4. 说明与变更记录（`PACK.md` / `CHANGELOG.md`，可选）
5. 签名（旁挂 `packhub.signatures.json`，或在清单里，可选）

### Assembly（整合）

整合是 Pack 的创作过程：挑资源、决定接线、叠加覆盖与调校，最后用锁把引用钉死。

产物是作者目录里的 Pack 目录，不是 `.phub`。整合回答「装什么、怎么接、为什么这么改」；打包只把结果运出去，安装只在目标环境里执行。

### Resource（资源）

Pack 里的一条能力声明，它相对于 Agent，而不是相对于整个 harness。所以它可以是 SKILL、工具、脚本、提示词……只要能让 Agent 稳定表现出某种能力；界面优化这类不算。

资源提供或需要的能力写成令牌，见 Composition 词条。资源可以用 `role: <角色名>` 声明自己占一个可替换角色——一个资源最多占一个角色，未选中的角色候选不进计划。

### Source（来源）

来源是资源对内容的引用：指向内容所在的位置，并且能取回来。

可以指向包内文件、代码仓库、包管理器或 URL。

### Composition（接线）

接线是资源之间的约束：谁提供什么能力（`provides`）、谁需要什么能力（`needs`）、哪个实现占用可替换角色（`roles` 与 `pick`）。

能力写成令牌 `<form>/<name>@<major>`（`tool/repo-search@1`、`skill/doc-review@1`）。`form` 是闭集 `tool` / `skill` / `content` / `config`，表示能力被消费的形态——工具调用、技能、可读内容、配置——**不是资源类型**：`mcp` / `tool2` 通常给 `tool/*`，`skill` 给 `skill/*`，`prompt` / `knowledge` 给 `content/*`，`config` 给 `config/*`。名字只描述能做什么，不泄漏资源类型；`@` 后是接口主版本（不小于 1 的整数），主版本不同就是两种能力。

`needs` 同时是能力依赖和安装顺序：每个被需要的令牌，其所有 provider 都排在消费者之前，成环报错。没有单独的 `dependsOn`。

一个角色是一个可替换位：清单用 `roles.<角色>.needs` 声明占位实现必须提供的能力，资源用 `role: <角色>` 占位。角色这次装哪个实现按这个次序定：`pick.<角色>` → `roles.<角色>.default` → 唯一候选。`pick` 覆盖 `default`；角色下只有一个候选时自动选它，不必写 `default`；候选多于一个又没写 `pick` / `default`，报 `role-unfilled`，提示写 `roles.<角色>.default` 或 `--pick`；角色下没有候选就是没人占它，不报错。被选中（含唯一候选自动选中）的实现必须存在、确实占用该角色、提供角色的全部 `needs`，否则报错；其余候选进计划的 `excluded`，原因 `not-selected`。

使用者可以在不改作者清单的前提下换实现：`packhub plan` / `packhub install` 的 `--pick <角色>=<资源>` 只覆盖这一次运行；项目内的长期覆盖写安装根 `.packhub/local.yaml` 的 `pick`，只影响这个项目，不写回清单，也不进锁与签名。

没有 `composition` 块：接线由 `provides` / `needs` / `roles` / `pick` 承载，再声明一份等于第二真相。接线图在计划期从清单派生（kernel 的 `describeComposition`，`plan` 打印出来），不落盘。

### Manifest（清单）

清单是 Pack 的书面声明：有哪些资源、彼此怎么接、有哪些约束。它不声明装到哪些 target——那属于安装参数，见 Target 词条。

它是打包的重要依据。

### Lock（锁）

锁是清单的一次解析结果：把引用钉死，并记下「清单 + pinned 引用」的内容哈希（`contentHash`），确保打包时的资源与版本一致，避免上游变动把包的功能弄坏。

锁只描述内容：不含安装 target，也不含任何计划。装到哪个 target、计划长什么样，是安装 / 校验那一刻按 target 现算的（见下 Plan）。

### Packaging（打包）

打包把已经整合、锁定好的 Pack 目录收成一个可交付文件：让包离开作者工作目录后仍然完整，能装到别的 harness 上。

清单、锁和要随包带走的内容进同一个归档。它只负责把包送到；

打包不负责整合：不挑资源、不改接线、不做调校，也不生成安装计划。默认自包含；

### Plan（计划）

计划是一次安装的动作安排：把 Pack 展开到某个目标上，列出要做哪些事、按什么顺序做。

计划是唯一描述副作用的东西，安装只是执行它。

计划是**按需现算**的产物：`planFor(ctx, { target })` 在用到它的那一刻按 target 算（不传就是 `dir`）——`plan` 预览、`install`、`diff`、`update`、`verify`、launcher 建/更新实例都各算一份；同一个 Pack 装到不同 target 会得到不同的计划与 `planHash`。锁和内容哈希都不含计划。

### Target（安装目标）

Target 是**安装 / 交付参数**：决定这次把这份内容落到哪个宿主形态——中性的 `dir`，或某个 harness（`dsh` / `claude-code` / `codex`）；不显式指定时是 `dir`。它由安装时选（`planFor(ctx, { target })`），不是 Pack 自带的属性。

它不属于 Pack 内容、不进锁、不进内容哈希：同一份内容装到不同 target，锁与签名不变；变的是落点与计划（`planFor` 现算）。

清单与资源都不声明安装形态：`schema/packhub.v0.schema.json` 的 `metadata` 只有 `name` / `version` 是必填、`additionalProperties: false`，资源条目也没有 `targets`——旧清单在这两处带 `targets` 会被判 schema error。装到哪个 target 只由安装时选。

`--target` 只决定目录内的落点形态：按哪个宿主的落点表物化文件、指令与 MCP 写法。它不等于有了一份宿主环境——home、进程、端口都不在目录里，装完只得到一份文件；要跑起来用实例（见 Launcher 词条）。

### Install（安装）

安装把 Pack 落进一个目录的过程：项目目录或实例根。内容展开到文件，登记写进该目录的 state。

安装只发生在目录，不在别处发生；全局环境不是安装的落点，而是实例的 home——要一份能跑起来的环境，用启动器建实例（见 Launcher 词条）。

安装是事务性的：要么全部成功，要么按快照回到安装前，不留半套。

### State（状态）

状态记录这台机器上已经发生了什么：装了哪个包、改写了哪些文件、每个动作的结果。

回滚、卸载、升级清理、漂移检查都读它；它是「装了什么」的唯一真相。

### Harness（宿主）

宿主是支持 Agent 运行的那一层，是整合包能够运行的底层。如果要比喻，就像 MC 的原版：不同的 harness 是不同实现或版本的 MC。

模型循环、工具执行、上下文、界面都在它那里。

宿主名同时是 target 的一种：装到某个 harness 上，就是按它的落点表物化；`dir` 是中性形态，不对应任何宿主（见 Target 词条）。

### Adapter（适配）

适配是 Pack 与某个宿主之间的翻译：把通用声明换成那个宿主认得的说法。

它只回答这个 Pack 在它上面能落成什么样——落点表、指令文件、MCP 写法、技能元数据。

### Instance（实例）

实例是宿主被启动之后的那份运行体：一个实例根，加上跑起来的进程与端口。

它同时有三样东西：配置（用哪个 Pack、什么宿主、根与 home 在哪）、数据（home 下的 skills、知识、会话、凭据、缓存）、运行态（进程、端口、地址、最近一次退出）。三样分开存放，运行态不混进配置。

实例不是 Pack 的一份拷贝：同一个 Pack 可以建多个实例，各自装、各自跑；实例也可以完全脱离 Pack 存在（接管来的目录）。

### Instance Record（实例记录）

启动器对每个实例维护两份记录：`instance.json` 只存配置，`runtime.json` 只存运行态。

两者之和才是「一份实例」；缺运行态就算坏记录，坏记录会被隔离到 `.quarantine/`，不会静默消失。

### Isolation（隔离）

隔离描述实例的每一层是独有还是跟宿主共用，共五层：装配产物、会话、凭据、取包缓存、宿主运行时。

默认是装配 / 会话 / 凭据每实例一份，缓存 / 运行时共用。策略在**建实例那一刻**快照进记录，之后改全局默认不追溯已有实例。

### Launcher（启动器）

启动器是实例的管理者，也是实例的启动者。实例是运行入口：要跑起来、要一份全局环境，都在实例上发生，不在目录里。

它列出、创建、复制、迁移、备份、删除实例；在实例上装、更新、卸载都从它发起——落点是实例根这个目录，写盘与登记仍走安装那一步。启动之后，实例的起停与异常归它照看。

实现上分两层：常驻的 core 独占启停与看护（CLI 只是它的客户端），core 被杀了由用户任务计划带回来。

### Registry（仓库）

一个用来存 Pack、维护不同版本的目录树：以 Pack 为最基础的操作单元，提供发布与读取。

包版本发布后不可变，改动要发新版本。读端是只读接口，写端是发布流程。
