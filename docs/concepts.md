# PackHub 概念

> 这份写「是什么、边界在哪」，不写怎么用；实现细节在代码与 [contract.md](contract.md) 里。市场部分已冻结，相关概念按现状描述。

### Pack（整合包）

一份可复用的 Agent 能力整合：不是把 Agent 需要的东西放在一起就够，而是这些功能能作为一个有机的整体给出。

Pack 不是资源的压缩包，哪怕有依赖关系也不自动成为有机整体；作为 Pack，需要创作者调整包内所有资源的关系，并以特定体验给出。

一个包内包括：

1. 清单 `packhub.yaml`
2. 锁 `packhub.lock.json`
3. 随包资源（`resources/`、`skills/`、`fragments/`、`glue/` 等）与补丁文件（目录名自选，`modify` 里按路径引用）
4. 说明与变更记录（`PACK.md` / `CHANGELOG.md`，可选）
5. 签名（旁挂 `packhub.signatures.json`，或在清单里，可选）

### Assembly（整合）

整合是 Pack 的创作过程：挑资源、决定接线、叠加覆盖与调校，最后用锁把引用钉死。

产物是作者目录里的 Pack 目录，不是 `.phub`。整合回答「装什么、怎么接、为什么这么改」；打包只把结果运出去，安装只在目标环境里执行。

### Resource（资源）

Pack 里的一条能力声明，它相对于 Agent，而不是相对于整个 harness。所以它可以是 SKILL、工具、脚本、提示词……只要能让 Agent 稳定表现出某种能力；界面优化这类不算。

### Source（来源）

来源是资源对内容的引用：指向内容所在的位置，并且能取回来。

可以指向包内文件、代码仓库、包管理器或 URL。v0 不做跨包引用，也不做继承。

### Composition（接线）

接线是资源之间的一组声明关系：谁提供什么能力、谁需要什么能力、谁占用哪个可替换位、谁依赖谁。

它只描述约束，由资源级的 `provides` / `needs` / `dependsOn` 与包级的 `slots` / `bindings` 承载，没有单独的 `composition` 块。

### Manifest（清单）

清单是 Pack 的书面声明：有哪些资源、彼此怎么接、装到哪些目标、有哪些约束。

它是打包的重要依据。字段与校验规则见 [contract.md](contract.md)。

### Lock（锁）

锁是清单的一次解析结果：把引用钉死、留下每个 target 的计划快照，确保打包时的资源与版本一致，避免上游变动把包的功能弄坏。

### Packaging（打包）

打包把已经整合、锁定好的 Pack 目录收成一个可交付文件：让包离开作者工作目录后仍然完整，能装到别的 harness 上。

清单、锁和要随包带走的内容进同一个归档。它只负责把包送到；装不装得进去，还要看目标在不在 Pack 声明的 `targets` 里。

打包不负责整合：不挑资源、不改接线、不做调校，也不生成安装计划。默认自包含；reference 模式只打清单与锁，要求所有来源都能在安装时远程取到，含本地来源时直接失败。

### Plan（计划）

计划是一次安装的动作安排：把 Pack 展开到某个目标上，列出要做哪些事、按什么顺序做。

计划是唯一描述副作用的东西，安装只是执行它。

### Install（安装）

安装把 Pack 落进一个根目录（项目目录或实例根）的过程，让宿主在那个环境里能用上 Pack 提供的能力。

安装是事务性的：要么全部成功，要么按快照回到安装前，不留半套。

### State（状态）

状态记录这台机器上已经发生了什么：装了哪个包、改写了哪些文件、每个动作的结果。

回滚、卸载、升级清理、漂移检查都读它；它是「装了什么」的唯一真相。

### Target（目标）

Target 决定「装到哪儿」：`dir` 只物化到项目内，`dsh` / `claude-code` / `codex` 另外写宿主认的落点（skills 目录、指令文件、MCP 配置）。

同一份清单在每个 target 上的计划不同；`lock` 会为每个声明过的 target 各存一份计划快照。

### Harness（宿主）

宿主是支持 Agent 运行的那一层，是整合包能够运行的底层。如果要比喻，就像 MC 的原版：不同的 harness 是不同实现或版本的 MC。

模型循环、工具执行、上下文、界面都在它那里。

### Adapter（适配）

适配是 Pack 与某个宿主之间的翻译：把通用声明换成那个宿主认得的说法。

它只回答这个 Pack 在它上面能落成什么样——落点表、指令文件、MCP 写法、技能元数据。

### Instance（实例）

实例是宿主被启动之后的那份运行体：一个实例根，加上跑起来的进程与端口。

它同时有三样东西：配置（用哪个 Pack、什么宿主、根与 home 在哪）、数据（home 下的 skills、知识、会话、凭据、缓存）、运行态（进程、端口、地址、最近一次退出）。三样分开存放，运行态不混进配置。

实例不是 Pack 的一份拷贝：同一个 Pack 可以建多个实例，各自装、各自跑；实例也可以完全脱离 Pack 存在（接管来的目录）。

### Instance Record（实例记录）

启动器对每个实例维护两份记录：`instance.json` 只存配置，`runtime.json` 只存运行态。

两者之和才是「一份实例」；缺运行态就算坏记录，不做旧格式兼容。记录坏了会被隔离到 `.quarantine/`，不会静默消失。

### Isolation（隔离）

隔离描述实例的每一层是独有还是跟宿主共用，共五层：装配产物、会话、凭据、取包缓存、宿主运行时。

默认是装配 / 会话 / 凭据每实例一份，缓存 / 运行时共用。策略在**建实例那一刻**快照进记录，之后改全局默认不追溯已有实例。

### Launcher（启动器）

启动器是实例的管理者，也是实例的启动者。

它列出、创建、复制、迁移、备份、删除实例；安装、更新、卸载从它发起，写盘与登记仍在安装那一步。启动之后，实例的起停与异常归它照看。

实现上分两层：常驻的 core 独占启停与看护（CLI 只是它的客户端），core 被杀了由用户任务计划带回来。

### Registry（仓库）

一个用来存 Pack、维护不同版本的目录树：以 Pack 为最基础的操作单元，提供发布与读取。

版本发布后不可变，改动要发新版本。读端是只读接口，写端与市场是另一件事。

### Market（市场）

市场原本设想在仓库之上提供上传、审核、统计、下架、账号与评分。
