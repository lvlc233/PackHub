# PackHub 竞品研究与功能架构整理

## 一、核心结论

PackHub 当前已经具备较完整的 Pack 制作、资源声明、依赖解析、安装、构建和分发能力，但跨 Harness 适配、实例管理和持续维护仍不完善。

PackHub 的核心定位是：

将 Skills、MCP、Prompts、配置及扩展资源组织为可复用的 Pack，通过依赖解析、冲突协调、兼容性适配与验证机制，将其部署为可维护、可升级、可恢复的 Agent 环境。

主要原则：

1. 整合而非简单打包：处理资源之间的依赖、冲突、接线与配置覆盖。
2. 适配而非重复开发：利用现有 Harness 的插件与包系统，处理其差异与共性。
3. 实例与 Pack 分离：一个 Pack 可以部署到不同 Harness，并创建多个独立实例。
4. 保留本地调校：实例修改不应在 Pack 更新时被直接覆盖。
5. 安装与验证分离：资源成功落地，不等于 Harness 已正确加载和使用。
6. 明确产品边界：管理 Agent 环境，不重新实现 Agent Runtime。

## 三、功能架构

保留现有功能域，将其组织为五个系统。

### 3.1 Pack Factory｜整合包制作

对应：PACK、DEP、RES

负责 Pack 从资源集合到整合包的过程。

主要能力：

- 资源组织：Skill、MCP、Prompt、Knowledge、Config、Tool 及扩展资源。
- 资源声明：元数据、来源、版本、完整性、目标 Harness。
- 依赖管理：依赖图、能力匹配、版本约束、安装顺序、可选依赖。
- 整合调校：资源接线、配置覆盖、条件组合、变体、第三方补丁。
- 冲突处理：文件冲突、配置冲突、互斥资源、冲突解决建议。
- 构建封装：Pack 结构、锁文件、归档、签名、vendored 资源。
- 制作工具：初始化、资源发现、结构化编辑、模板、导入导出。

目标：让多个独立资源形成经过组织、适配和调校的整合包。

### 3.2 Compatibility Engine｜跨 Harness 适配

对应：ADP、VAL

负责将 Pack 映射到不同 Harness，并验证结果。

主要能力：

- Harness 发现：检测安装位置、版本、能力及版本差异。
- 落点映射：Skills、MCP、指令文件、插件与配置的目标位置。
- 格式转换：JSON、YAML、TOML、托管块与配置合并。
- 资源适配：不同 Harness 的资源格式、目录结构与功能差异。
- 兼容性处理：能力缺失、不可移植资源、降级声明与差异报告。
- 验证：静态检查、安装验证、运行探针、行为验证、漂移检测。

适配器需要覆盖的操作：

| 操作       | 职责                 |
| -------- | ------------------ |
| Discover | 发现 Harness、版本及安装位置 |
| Plan     | 生成资源与配置修改计划        |
| Validate | 检查兼容性和安装条件         |
| Apply    | 执行安装，优先调用宿主 CLI    |
| Verify   | 验证安装、加载及行为结果       |
| Rollback | 恢复失败前的状态           |
| Diagnose | 解释错误并提供处理建议        |

兼容性与验证使用统一的五级判定：

| 等级 | 含义             |
| -- | -------------- |
| L0 | 可安装            |
| L1 | 可启动或读取相关配置     |
| L2 | 资源可用           |
| L3 | 跨 Harness 语义保持 |
| L4 | 实际行为符合预期       |

其中 ADP 负责能力与兼容性判断，VAL 负责采集验证证据，避免重复实现两套判定逻辑。

### 3.3 Instance Manager｜实例管理

对应：INS、IST、REL、LCM

负责 Pack 的安装、实例化和持续维护。

主要能力：

- 安装：来源解析、预检查、安装计划、执行、回滚、断点恢复、幂等。
- 实例管理：创建、复制、重命名、删除、隔离、运行时共享。
- 实例状态：配置、数据、密钥、缓存、端口、进程与会话历史。
- Pack 关系：版本基线、本地修改检测、覆盖保护、重新基准化。
- 生命周期：更新检查、差异分析、依赖升级、数据迁移、回滚。
- 实例复用：快照、模板、分叉、导入导出、迁移。

核心关系：

```
Pack
  ├── Codex Instance A
  │     ├── Pack 基线
  │     ├── Harness 适配配置
  │     └── 本地修改
  │
  ├── Codex Instance B
  │     └── 独立配置与状态
  │
  └── OpenCode Instance C
        ├── Pack 基线
        └── Harness 适配配置
```

一个 Pack 可以产生多个实例。实例独立保存状态和修改，并保留与上游 Pack 的关系。

特别需要关注 REL：

- REL-01：记录 Pack 基线。
- REL-02：检测用户本地修改。
- REL-03：保护本地修改。
- REL-04：在上游更新后重新基准化。

这四项决定了整合包能否在用户调校之后继续升级和维护。

### 3.4 Launcher｜启动与运行

对应：LCH、SYN

负责环境准备、Harness 启动、运行诊断及全局资源同步。

主要能力：

- Harness 发现、安装与版本切换。
- 启动前检查与自愈。
- 启动参数和环境变量管理。
- 进程、端口、退出状态管理。
- 日志采集与崩溃诊断。
- 重启与守护。
- 启动后交接 CLI、TUI 或 Web UI。
- 全局 Skills、MCP、指令文件同步。
- 公共技能目录支持。

Launcher 不需要重新实现 Harness 的 Agent 运行时或交互界面。

### 3.5 Platform｜公共基础设施

对应：REG、SEC、SYS、UI

负责为其他系统提供通用能力。

| 功能域 | 主要职责                           |
| --- | ------------------------------ |
| REG | Registry、搜索、版本分发、外部导入、签名和私有源   |
| SEC | 完整性、权限、凭据保护、宿主文件保护、审计          |
| SYS | 跨平台文件系统、进程、网络、持久化、并发、测试        |
| UI  | Pack 浏览、实例管理、安装向导、兼容性解释、日志、创作台 |

### 值得复用的机制

1. 共享运行时与实例隔离：实例拥有独立配置和状态，运行时可以共享。
2. 每个 Harness 独立管理写入位置与状态：避免跨 Harness 同步和卸载相互干扰。
3. 符号链接与复制策略：优先保留共享关系，必要时复制。
4. 改写前备份：保留宿主原始配置，避免丢失用户数据。
5. 可信包契约：Manifest、逐文件完整性、容量限制和失败拒绝。
6. 恢复结果验证：不能确认恢复成功时明确标注未确认。
7. 多来源导入：支持将现有外部资源包或配置转换为 Pack。
8. 启动前自愈：检查并修复可恢复的配置或文件问题。
9. 保留用户修改的合并策略：避免直接覆盖本地状态。
10. 错误诊断：将日志和异常信息转化为可操作的结论。

### PackHub 的差异化

- 整合包契约：Pack 具有版本、锁文件、依赖关系和验证报告。
- 跨 Harness 适配：同一 Pack 可映射到不同 Harness，并明确兼容差异。
- 实例与上游关系：记录本地修改，支持升级、重新基准化及分叉。
- 可验证性：不仅检查文件是否存在，还检查资源能否被宿主识别和使用。

## 五、开发中需要统一的公共机制

多个功能域涉及相同的底层能力，应当共享实现，避免重复维护。

| 公共机制         | 涉及功能域            |
| ------------ | ---------------- |
| 托管块读写        | PACK、ADP、SYN、REL |
| 三方合并         | ADP、REL、LCM      |
| 引用计数         | IST、INS、LCM      |
| 安装事务与回滚      | INS、SYN、LCM      |
| Harness 能力注册 | ADP、DEP、VAL      |
| 资源完整性检查      | PACK、REG、SEC、VAL |
| 安装计划与差异分析    | DEP、INS、REL、LCM  |

原则：公共机制独立实现，具体功能域复用，不重复维护相同逻辑。

## 七、开发关注顺序

以下仅重新组织已有建议，不增加新的功能项。

### 第一部分：现有功能正确性

- JSON 错误解析。
- 安装目标与验证目标一致性。
- 依赖字段语义。
- 探针前置条件与副作用。
- 宿主文件备份与安装恢复。

### 第二部分：跨 Harness 适配与资源整合

- Harness 发现与能力清单。
- 公共资源目录及目标映射。
- 配置格式转换与合并。
- 资源依赖、冲突与覆盖。
- 兼容性判定与差异报告。
- 真实 Harness 验证。

### 第三部分：Pack 与实例的持续关系

- Pack 基线与本地修改记录。
- 本地修改保护。
- 上游更新与重新基准化。
- 实例创建、隔离与共享运行时。
- 快照、回滚和迁移。

### 第四部分：启动、交互与分发

- Harness 启动、检查、自愈和诊断。
- 实例与 Pack 的界面管理。
- 资源分发、导入导出与同步。
- 更新通知与生命周期管理。

## 八、产品边界

### PackHub 负责

- Pack 的制作、整合、构建与发布。
- Agent 资源的组织、依赖、冲突和配置协调。
- 跨 Harness 适配。
- Pack 的安装、实例化和维护。
- 资源及环境验证。
- 与整合包生命周期有关的启动和诊断。

### PackHub 不负责

- 模型网关与 Provider 路由。
- Agent Loop、任务编排和工具执行引擎。
- 上下文压缩、记忆算法。
- 完整会话浏览、恢复和聊天客户端。
- 代码编辑器与 LSP。
- Harness 原生插件的运行引擎。
- Minecraft 专有的 Java、加载器和版本逻辑。

PackHub 可以安装、配置和检查这些能力所需的资源，但不需要自己实现其内部功能。

## 九、总结

当前 PackHub 已经建立了较好的 Pack 制作与发布基础。

接下来的主要工作集中在：

1. ADP：跨 Harness 适配——解决同一 Pack 如何适配不同 Harness。
2. REL：Pack 与实例关系——解决本地调校、上游更新及修改保留。
3. VAL：验证与测试——解决资源安装后是否实际可用。
4. IST：实例管理——解决多实例隔离、共享与生命周期维护。
5. LCH：启动与诊断——解决实例环境准备、启动和故障定位。

整体目标是从当前的 Pack 制作、安装与分发工具，逐步形成完整的 Agent 整合包管理系统。
