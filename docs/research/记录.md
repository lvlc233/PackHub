# 记录

## 一、核心结论

PackHub 当前已经具备较完整的 Pack 制作、资源声明、依赖解析、安装、构建和分发能力，但跨 Harness 适配、实例管理和持续维护仍不完善。

**产品定位：** 将 Skills、MCP、Prompts、配置及扩展资源组织为可复用的 Pack，通过依赖解析、冲突协调、兼容性适配与验证机制，将其部署为可维护、可升级、可恢复的 Agent 环境。

主要原则：

1. **整合而非简单打包**：处理资源间的依赖、冲突、接线和配置覆盖。
2. **适配而非重复开发**：利用 Harness 现有插件与包系统，处理其差异与共性。
3. **实例与 Pack 分离**：同一个 Pack 能面向不同 Harness 创建多个实例。
4. **保留本地调校**：Pack 更新不应直接覆盖实例中的用户修改。
5. **安装与验证分离**：文件成功落地，不代表 Harness 已正确加载和使用。
6. **明确产品边界**：管理 Agent 环境，不重新实现 Agent Runtime。

## 三、功能架构

保留原有功能域，将其组织为五个系统。

### 3.1 Pack Factory｜整合包制作

**对应：PACK、DEP、RES**

负责 Pack 从资源集合到整合包的过程。

- **资源组织**：Skill、MCP、Prompt、Knowledge、Config、Tool 及扩展资源。
- **资源声明**：元数据、来源、版本、完整性、目标 Harness。
- **依赖管理**：依赖图、能力匹配、版本约束、安装顺序、可选依赖。
- **整合调校**：资源接线、配置覆盖、条件组合、变体、第三方补丁。
- **冲突处理**：文件冲突、配置冲突、互斥资源、冲突解决建议。
- **构建封装**：Pack 结构、锁文件、归档、签名、vendored 资源。
- **制作工具**：初始化、资源发现、结构化编辑、模板、导入导出。

**版本求解（DEP-04）**

- 多个资源对同一依赖提出版本范围时，求解满足约束的版本；优先级为已锁版本、最新稳定版本、其他可行版本。
- 无解时输出冲突约束；求解超时则明确报告未能求解。
- 将最终版本写入锁文件，避免版本漂移。

**单资源更新（RES-06）**

- 解析资源上游版本或 commit、取得制品并检查 integrity。
- 比较文件差异，识别 frontmatter 变化、入口文件消失、依赖新增等破坏性变更。
- 只更新目标资源的锁定引用和安装计划，重跑验证；其他资源不应无故改变版本。

**核心目标：** 让多个独立资源形成经过组织、适配和调校的整合包。

### 3.2 Compatibility Engine｜跨 Harness 适配

**对应：ADP、VAL**

负责将 Pack 映射到不同 Harness，并验证结果。

- **Harness 发现**：检测安装位置、版本、能力及版本差异。
- **落点映射**：Skills、MCP、指令文件、插件与配置的目标位置。
- **格式转换**：JSON、YAML、TOML、托管块与配置合并。
- **资源适配**：资源格式、目录结构与功能差异。
- **兼容性处理**：能力缺失、不可移植资源、降级声明与差异报告。
- **验证**：静态检查、安装验证、运行探针、行为验证、漂移检测。

**Harness 能力清单（ADP-01.2）**

- 对每种 Harness 维护能力基线，包含指令文件与托管块、Skills 目录和 frontmatter、MCP 配置路径/格式/作用域、hooks、权限、无头入口及输出格式、会话与插件能力。
- 运行时探测实际版本、资源目录和无头入口；与基线冲突时以实测为准并标记差异。
- 适配逻辑共用能力清单，不在多个位置分别硬编码判断。

**适配器操作**

| 操作 | 职责 |
|---|---|
| Discover | 发现 Harness、版本及安装位置 |
| Plan | 生成资源与配置修改计划 |
| Validate | 检查兼容性和安装条件 |
| Apply | 执行安装，优先调用宿主 CLI |
| Verify | 验证安装、加载及行为结果 |
| Rollback | 恢复失败前的状态 |
| Diagnose | 解释错误并提供处理建议 |

**兼容性判定（ADP-05.1、VAL-04）**

| 等级 | 判定条件 |
|---|---|
| L0 | 计划可生成、资源可获取且无阻断性冲突 |
| L1 | Harness 可启动，并能读取相关托管指令 |
| L2 | 所需资源在 Harness 中可见或可用，如 Skill 列表可见、MCP 握手成功 |
| L3 | Pack 声明的语义断言经 scenario 检查成立 |
| L4 | 跨 Harness 的相同 scenario 均通过 |

- ADP 负责能力与兼容性判断，VAL 负责采集证据，共用同一套等级判定。
- 安装后默认验证到 L2；L3/L4 通过深度检查或 CI 执行。
- 无头入口不可用时，相关证据标为 `unverified`，不能直接宣称通过。

### 3.3 Instance Manager｜实例管理

**对应：INS、IST、REL、LCM**

负责 Pack 安装、实例化和持续维护。

- **安装**：来源解析、预检查、安装计划、执行、回滚、断点恢复、幂等。
- **实例管理**：创建、复制、重命名、删除、隔离、运行时共享。
- **实例状态**：配置、数据、密钥、缓存、端口、进程与会话历史。
- **Pack 关系**：版本基线、本地修改检测、覆盖保护、重新基准化。
- **生命周期**：更新检查、差异分析、依赖升级、数据迁移、回滚。
- **实例复用**：快照、模板、分叉、导入导出、迁移。

**实例化与状态（INS-13）**

- 实例记录字段：`id`、`name`、`harness`、`harnessVersion`、`packRef`、`packVersion`、`planHash`、`root`、`ports`、`createdAt`、`status`。
- 状态流：`created → installing → installed → running → stopped → broken → removed`。
- 实例根目录组织数据、配置、缓存、日志、状态五类内容；不同 Harness 的实例外部落点由适配器确定，不假定全部路径在实例根下。
- 安装完成写入实例记录和基线；失败时将未完成的实例目录移入 `quarantine/<id>`，避免半成品误用。

**安装事务和断点恢复（INS-04、INS-07）**

- `staging/<txn-id>/` 暂存动作结果，`snapshots/<generation>/` 保存原文件，`installing.lock` 协调并发安装。
- 提交顺序为新建文件、替换旧文件、写入 `state.json`；操作失败进入回滚流程，不提前标记安装成功。
- staging 与目标位于同一磁盘，减少跨盘 rename 问题；Journal 记录文件提交进度以处理进程被杀或断电。
- `journal.jsonl` 记录动作开始和结束，区分 `not-started / started / done`；可安全重放的动作继续执行，其余按快照回滚。
- 已下载且哈希校验通过的资源不重复下载；Journal 损坏时只使用最后一条完整记录之前的数据。

**隔离与共享（IST-05、IST-06）**

- 配置、数据、密钥、缓存、端口、进程分别确定隔离落点；会话历史亦须纳入实例隔离边界。
- 采用 per-harness 路径表，不统一承诺所有 Harness 的密钥能隔离在实例内部。
- 资源区分 `owned` 与 `shared`；卸载只直接删除 owned，shared 通过引用计数回收。
- 运行时存放在版本化槽位，实例通过 `runtimeRef` 绑定具体版本；切换全局 `active` 仅影响新实例。
- 没有实例引用的运行时版本才可回收。

**Pack 基线与本地调校（REL-01～04）**

- 安装完成写 `baseline.json`，记录 `packRef`、`packVersion`、`planHash`、安装时间、托管文件及其哈希、配置键。
- 基线不随实例内的用户修改自动更新；丢失时可尝试从安装状态恢复。
- 比较旧基线、当前实例与新版 Pack：用户未改而上游改的使用上游；用户改而上游未改的保留用户；双方都改则输出冲突并允许逐文件/逐键处理。
- 默认保留用户修改并标记冲突；配置按键合并，写回前先快照；托管块外的用户内容不得随意改写。

**实例关系**

```text
Pack
  ├── Codex Instance A
  │     ├── Pack 基线
  │     ├── Harness 适配配置
  │     └── 本地修改
  ├── Codex Instance B
  │     └── 独立配置与状态
  └── OpenCode Instance C
        ├── Pack 基线
        └── Harness 适配配置
```

**实例迁移（IST-08）**

- 迁移前统计文件数、符号链接、硬链接与大小。
- 迁移时保留链接语义，不将其摊平成重复文件；重定位指向旧根的绝对路径。
- 迁移后检查文件和链接数量、关键文件哈希及启动结果；失败时保留原目录，不切换实例记录。

**核心目标：** Pack 可产生多个独立实例，并在本地修改、更新、迁移和回滚后持续可维护。

### 3.4 Launcher｜启动与运行

**对应：LCH、SYN**

负责环境准备、Harness 启动、运行诊断及全局资源同步。

- Harness 发现、安装与版本切换。
- 启动前检查与自愈。
- 启动参数和环境变量管理。
- 进程、端口、退出状态管理。
- 日志采集与崩溃诊断。
- 重启与守护。
- 启动后交接 CLI、TUI 或 Web UI。
- 全局 Skills、MCP、指令文件同步与公共技能目录支持。

**启动前自愈（LCH-02）**

- 检查托管块缺失或截断、Skill 链接缺失、僵尸锁、配置键缺失、端口占用。
- 按基线恢复可修复内容，重建链接、回收僵尸锁，必要时调整端口；涉及配置修改时保留用户修改保护。
- 记录修复动作与结果；失败时明确标注异常状态。

**进程和崩溃诊断（LCH-04、LCH-07）**

- 记录 PID、启动时间、退出码和运行耗时；采集 stdout/stderr，进行脱敏及轮转。
- 非正常退出时按已知错误模式匹配原因和处理建议；无法匹配时展示原始日志，不编造结论。
- 对 JSON 错误体解析结构化 `message/ref`，避免仅截取最后一行。
- Windows 环境单独处理终止和子进程树回收。

Launcher 不需要重新实现 Harness 的 Agent 运行时或交互界面。

### 3.5 Platform｜公共基础设施

**对应：REG、SEC、SYS、UI**

| 功能域 | 主要职责 |
|---|---|
| REG | Registry、搜索、版本分发、外部导入、签名和私有源 |
| SEC | 完整性、权限、凭据保护、宿主文件保护、审计 |
| SYS | 跨平台文件系统、进程、网络、持久化、并发、测试 |
| UI | Pack 浏览、实例管理、安装向导、兼容性解释、日志、创作台 |

**扩展安全（SEC-07）**

- 标注 `exec`、网络访问、实例外路径写入等风险；安装期脚本必须经明确批准。
- 安装期受限执行环境不继承宿主凭据。
- 将 Pack 声明权限与 Harness 实际权限对照，超出部分明确警告。
- 各 Harness 安全边界不同；Pi 无内置权限系统，隔离依赖外部容器环境。

**外部生态导入（REG-09）**

- 识别 CC Switch 项目、Pi package、mrpack 式清单，将可映射的资源与配置转为 Pack 草稿。
- 无法映射的内容列出原因；CC Switch 的 Provider 配置不属于核心导入范围。
- 导入生成草稿，不直接发布。

## 四、竞品研究与可借鉴机制

| 竞品 | 核心能力 | 借鉴方向 | 对应功能域 |
|---|---|---|---|
| PCL | 整合包安装、实例列表、崩溃分析 | 安装流程、实例交互、错误诊断 | INS、IST、LCH |
| PCL-DSH | 多实例、共享运行时、快照、自愈 | 实例隔离与生命周期 | IST、LCM、LCH |
| CC Switch | 多 Harness 配置、同步、备份 | 配置映射、安全写入、公共目录 | ADP、SYN、SEC |
| Pi packages | 多资源包、扩展加载与分发 | 包结构、资源声明、加载机制 | PACK、RES、DEP |
| Codex Multi Launcher | 独立 HOME、账户与会话 | 实例隔离边界 | IST |
| Codex Dream Skin | Manifest、哈希、完整性校验、恢复 | 可信安装与失败恢复 | SEC、INS、VAL |
| AionUi | 多 Agent 统一客户端 | 明确运行界面与 Pack 管理的边界 | LCH、UI |
| Aidevix CLI | CLI 发现、安装与启动 | 启动器的职责范围 | LCH |

**值得复用的机制：**

1. 共享运行时与实例隔离，兼顾磁盘成本和独立状态。
2. 每个 Harness 独立管理写入位置与状态，避免同步、卸载相互干扰。
3. 符号链接优先、复制兜底，保留资源共享语义。
4. 首次改写宿主文件前备份。
5. 资源包契约、逐文件完整性、容量限制与失败拒绝。
6. 恢复结果需验证；不能确认时明确标注未确认。
7. 多来源导入现有资源和配置。
8. 启动前检查并修复可恢复问题。
9. 合并时保留用户修改，而非直接覆盖。
10. 把错误日志转成可操作的结论。

**PackHub 的差异化：**

- **整合包契约**：版本、锁文件、依赖与验证报告。
- **跨 Harness 适配**：同一个 Pack 映射到不同 Harness，明确差异及降级。
- **实例与上游关系**：保留本地调校，支持升级、重新基准化和分叉。
- **可验证性**：检查资源是否被实际识别和使用，而不只检查文件存在。

## 五、开发中需要统一的公共机制

| 公共机制 | 涉及功能域 | 统一约束 |
|---|---|---|
| 托管块读写 | PACK、ADP、SYN、REL | 只改托管范围，保留块外内容 |
| 三方合并 | ADP、REL、LCM | 旧基线 / 当前实例 / 新版本；冲突默认保护用户修改 |
| 引用计数 | IST、INS、LCM | 区分 owned/shared，避免共享资源被误删 |
| 安装事务与回滚 | INS、SYN、LCM | Staging、Snapshot、Journal、安装锁、状态提交顺序 |
| Harness 能力注册 | ADP、DEP、VAL | 能力基线表与运行时探测统一管理 |
| 资源完整性检查 | PACK、REG、SEC、VAL | 对制品和恢复结果进行验证 |
| 安装计划与差异分析 | DEP、INS、REL、LCM | 同一份计划与差异信息服务于安装、升级和实例维护 |

**原则：** 公共机制独立实现，具体功能域复用，不重复维护相同逻辑。

## 七、开发关注顺序

以下仅组织已有任务，不新增功能。

### 第一部分：现有功能正确性

- JSON 错误解析。
- 安装目标与验证目标一致性。
- 依赖字段语义。
- 探针前置条件与副作用。
- 宿主文件备份与安装恢复。

### 第二部分：跨 Harness 适配与资源整合

- Harness 发现与能力清单。
- 公共资源目录及目标映射。
- 配置格式转换与合并。
- 资源依赖、冲突与覆盖。
- 兼容性判定与差异报告。
- 真实 Harness 验证。

### 第三部分：Pack 与实例的持续关系

- Pack 基线与本地修改记录。
- 本地修改保护。
- 上游更新与重新基准化。
- 实例创建、隔离与共享运行时。
- 快照、回滚和迁移。

### 第四部分：启动、交互与分发

- Harness 启动、检查、自愈和诊断。
- 实例与 Pack 的界面管理。
- 资源分发、导入导出与同步。
- 更新通知与生命周期管理。

---

## 八、产品边界

### PackHub 负责

- Pack 的制作、整合、构建与发布。
- Agent 资源的组织、依赖、冲突和配置协调。
- 跨 Harness 适配。
- Pack 的安装、实例化和维护。
- 资源及环境验证。
- 与整合包生命周期有关的启动和诊断。

### PackHub 不负责

- 模型网关与 Provider 路由。
- Agent Loop、任务编排和工具执行引擎。
- 上下文压缩、记忆算法。
- 完整会话浏览、恢复和聊天客户端。
- 代码编辑器与 LSP。
- Harness 原生插件的运行引擎。
- Minecraft 专有的 Java、加载器和版本逻辑。

PackHub 可以安装、配置和检查这些能力所需的资源，但不需要自己实现其内部功能。

---

## 九、总结

当前 PackHub 已经建立了较好的 Pack 制作与发布基础。后续主要工作集中在：

1. **ADP：跨 Harness 适配**——解决同一个 Pack 如何适配不同 Harness。
2. **REL：Pack 与实例关系**——解决本地调校、上游更新及修改保留。
3. **VAL：验证与测试**——解决资源安装后是否实际可用。
4. **IST：实例管理**——解决多实例隔离、共享与生命周期维护。
5. **LCH：启动与诊断**——解决实例环境准备、启动和故障定位。

目标是从当前的 **Pack 制作、安装与分发工具**，逐步形成完整的 **Agent 整合包管理系统**。
