# 0.0.2 产品形态：一个内核，三张脸

> 修正：上一版把 B/C/D 当成互斥选项来选，错了。
> A 是内核（必然包含），B、C、D 是**不同角色的入口**。要定的不是「做哪个」，而是「先给谁做、共享什么、按什么顺序长出来」。

---

## 一、按人分，不按形态分

| 角色 | 他的问题 | 他该碰到的脸 | 现在有什么 |
|---|---|---|---|
| **作者**（会写 YAML 的人） | 这堆资源怎么组合、接线对不对、怎么发出去 | D 编辑器 + CLI `publish` | CLI 能 plan/install/verify；没有发布，没有编辑器 |
| **开发者使用者**（在项目里装包的人） | 哪个包能解决我的问题、敢不敢装、装完对不对 | B 目录站 + A CLI | CLI 能装本地包；没有站，远程资源刚能下 |
| **非工程使用者**（不碰命令行的人） | 图形点两下装上、看得懂发生了什么 | C 桌面启动器 | 只有 demo |

三个角色共用同一个内核，但**判断只写一次**。

---

## 二、四个形态其实是四层

```
L3 外壳     CLI 二进制        桌面 App（webview）     静态站（Pages）
              │                     │                     │
L2 视图     /（作者调试）        /（我的项目）          /packs  /packs/:name  /edit
              └──────────── 同一个 React 应用，不同路由 ────────────┘
              │                     │                     │
L1 契约     Plan · Lock · State · Index  四份 JSON（带版本号）+ 本地 HTTP 服务
              │
L0 内核     @packhub/core：解析 · 能力图 · 计划 · 应用 · 校验 · 锁
```

硬约束（这几条决定了以后能不能只写一遍）：

1. **视图层不许有判断**。能不能装、装没装上、校验过没过，全部来自 L0/L1；视图只做映射和展示。
2. **外壳不许有业务**。CLI 是 `core` 的薄命令；桌面壳是 webview + 本地服务；静态站是构建产物。
3. **契约版本化**。`plan/lock/state/index` 各自带 `apiVersion`，破坏性改动升主版本。
4. **一个 React 应用**，路由分三种：`/` 作者座舱、`/packs` 公开目录与包页、`/edit` 可视化编辑器。桌面壳在 webview 里加载同一份产物。

## 三、0.0.2 只推一条线：使用者线

理由：作者线和桌面线都卡在「没有可分发的包」上；而使用者线恰好是当前唯一的空白（README 三价值里的「分发」）。

**0.0.2 的范围**

| 优先级 | 事项 | 交付 |
|---|---|---|
| P0 | 契约冻结 + 服务文档化 | `docs/contract.md`：四份 JSON 的字段与版本；`/api/*` 的请求响应 |
| P0 | registry 仓库 | `packs/<scope>/<name>/` + CI（schema · pin · integrity · verify）+ `index.json` 生成 |
| P0 | `packhub add/update/remove` | 从 `registry:name`、`git+https://`、`./x.phub` 三种入口安装 |
| P1 | 公开目录与包页（B） | `/packs`、`/packs/:scope/:name`：解决什么、物料清单、验证报告、复制命令 |
| P1 | verified 判定 | CI 在干净容器跑 verify，报告随版本存档，页面展示报告摘要 |
| P2 | 桌面壳的**准备** | 保证同一 Web 产物能在 webview 跑、只依赖本地 `/api`；不做打包 |
| P3 | 作者模式（D） | `/edit` 路由 + manifest 双向同步；放 0.0.3 |

**0.0.2 明确不做**：Tauri/Electron 打包、账号体系、评分评论、在线安装、自动依赖求解。

## 四、验收标准（不达标就是没做完）

1. 一个没听过这个项目的人，拿到一条 `npx packhub add lvlc233/code-review`，5 分钟内装进自己的项目，`packhub verify` 全绿。
2. 一个作者，10 分钟内把自己写的 Pack 发成 PR，CI 通过，包页上线，别人能装。
3. 两个人装同一个包，`planHash` 一致；页面上的 verified 报告与本地 verify 结果对得上。

这三条全部围绕「分发」——这是 0.0.2 唯一要证明的事。

---

## 五、之后按什么顺序长

| 版本 | 主题 | 依据 |
|---|---|---|
| 0.0.2 | 分发闭环（B + A） | 现在缺的就是这个 |
| 0.0.3 | 作者线（D + publish 体验） | 有内容之后，作者才会来优化组合 |
| 0.0.4 / 0.1 | 桌面壳（C） | 有人真的在用、且不愿意开终端时才有意义 |

判断依据很简单：**哪条线能带来「第二个使用者」，就先做哪条**。桌面壳在只有你一个人用的时候，永远排最后。
