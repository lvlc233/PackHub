# 0.0.2 产品形态提案

> 0.0.1 证明了内核能跑：解析 → 计划 → 安装 → 校验。但没有分发，它只是一台本地的 YAML 检查器。
> 0.0.2 要定的不是功能清单，是**用户接触到 PackHub 的那一层长什么样**。

---

## 一、先把「形态」问清楚

现在有四个可能的正面：

| 形态 | 用户怎么接触 | 交付物 | 工程量 | 与现有资产的关系 |
|---|---|---|---|---|
| **A 命令行包管理器** | `packhub search / add / update` | 一条命令 | 小 | 内核几乎全部复用 |
| **B 目录站 + 一行安装** | 先看网页，再复制命令 | 一个页面 + 一条命令 | 中 | 面板改造成公开页 |
| **C 桌面启动器** | 一个应用窗口 | 图形化装包 | 大 | 需要新壳（Tauri/Electron） |
| **D 可视化编辑器** | 拖拽组合资源 | 一个 Pack 文件 | 大 | 内核复用，交互全新 |

**我的判断：B。** 理由三条：

1. README 的三个价值里，前两个（聚合、整合）已经在内核里成立，只有**分发**是空的。没有分发，用户为什么要用别人的包？没有包可看，网页也只是一个空壳。
2. C 和 D 都是「没有内容生态时的空壳」：桌面启动器在只有两个示例包时，没有任何理由让人下载一个 80MB 的安装包。B 是唯一能先长出内容的形态。
3. B 让面板从「本地调试工具」升级成「产品正面」，而复用同一套组件——一个 React 应用，两种模式（本地座舱 / 公开包页）。

## 二、B 形态长什么样（用户脚本）

```
① 打开 packs.packhub.dev  →  搜「代码审查」
② 包页告诉你：解决什么问题 / 由哪 4 个资源组成（含 pin）/ 谁验证过 / 最近验证时间
③ 复制命令：npx packhub add lvlc233/code-review
④ 本地打印计划（会装什么、写哪些文件）→ 确认 → 装
⑤ packhub verify → 出报告，和页面上那枚 verified 徽章对得上（同一个 planHash）
```

作者侧：

```
packhub publish → 向 registry 仓库提 PR → CI 在干净环境跑 schema/pin/verify → 合并 → 索引重建
```

**形态的四个硬约定**（这些是产品，不是实现细节）：

1. **安装入口只有三种**：`registry:scope/name`（有索引）、`git+https://...`（无索引，直接装）、`./x.phub`（本地归档）。不做第四种。
2. **页面不提供在线安装**：网页只给命令。安装永远发生在用户机器上——这是「不托管、不接管执行」的边界。
3. **可信只有两档**：`verified`（CI 在干净容器里 verify 全绿）与 `community`（其余）。没有五星评分，没有评论。
4. **公开页与本地座舱共用一个组件库**：包页 = 本地面板去掉「本机状态」那块，加上「验证报告 / 安装命令 / 作者」。

## 三、0.0.2 的范围（一个闭环，不铺开）

必做，按依赖顺序：

1. **`fetch` 实装**：远程资源真能下（npm / pypi / github / https），流式 sha256 校验，解包。现在这一步是「跳过」，分发之前必须先补上。
2. **`pack` 归档**：出 `.phub`（reference / vendored 两种）。
3. **`publish` + registry 仓库**：`packs/<scope>/<name>/` + CI 校验 + `index.json` 生成 + Pages 部署。
4. **`add` / `remove` / `update`**：从 registry 或 git URL 拉 manifest、写 lock、装到项目；`update` 用 plan 对比给出差异。
5. **公开站两个页**：列表（搜索/筛选 target）+ 包页（物料清单、能力图、验证报告、复制命令）。
6. **3 个种子包**：代码审查（已有）、团队约定（已有）、再加一个只用 MCP 的。

明确不做：账号、评分、评论、在线编辑、服务端依赖解析、桌面应用。

## 四、这版必须回答的产品问题

| # | 问题 | 我的建议 |
|---|---|---|
| P1 | 公开站的域名与身份 | 先 GitHub Pages 子域，等有一个真实验证过的包再谈域名 |
| P2 | verified 的判定标准 | CI 在干净容器：schema + pin 完整 + integrity 匹配 + verify 全绿；报告随版本存档 |
| P3 | 包页要不要展示「装了什么文件」 | 要。这是 Pack 与「一堆链接」的分界，也是用户敢装的理由 |
| P4 | 本地座舱是否还保留 | 保留，但降级为作者调试工具（`packhub serve`），不再是产品正面 |
| P5 | 版本号节奏 | 0.0.2 = 分发闭环；0.0.3 再谈「组合可视化」 |

## 五、四个形态已经做成了可以点的 demo

`pnpm serve` 之后打开：

| 形态 | 地址 | 看什么 |
|---|---|---|
| A 命令行 | `/forms/a` | 没有网页时，用户一天里实际看到的东西 |
| B 目录站 + 一行安装 | `/forms/b` | 发现 + 信任 + 复制命令，是否比 A 多解决了「我为什么要装它」 |
| C 桌面启动器 | `/forms/c` | 图形化装包体验的真实密度（列表、进度、写哪些文件） |
| D 可视化编辑器 | `/forms/d` | 作者侧的搭积木手感，能力连线是否成立 |

四个 demo 共用同一套 token（`packages/web/src/styles.css`），但**只有 B 的包页可以长成正式产品**；C 和 D 的窗口外壳是画的，不是真应用。数据全部来自 `examples/` 与真实 manifest 结构。

## 六、关于「AI 质感」

你说得对。当前这版是「合格但通用」：好看的间距、统一的圆角、常见的紫。它不是坏的，但没有身份。

这类工具的身份不该由装饰给出，而该由**它展示的东西**给出——0.0.2 的公开包页正好承载这件事：一个包解决的问题、它替你做过的适配、验证证据、以及 who verified it。等有了真实内容，再谈视觉上的辨识度，比现在空着页面调色更有效。

在 0.0.2 之前，我不建议再改本地座舱的视觉。
