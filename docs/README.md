# PackHub 文档

> 只留三份，都对着代码：概念、契约、台账。
> 面向使用者的说明（怎么装、参数什么意思、怎么写包）在行为稳定之前不写——错的说明比没有说明更贵。命令看 `packhub <命令> --help`。
> 历史不进 `docs/`，`git log -- docs/` 里查。

| 文档 | 管 | 不管 |
|---|---|---|
| [concepts.md](concepts.md) | 概念、边界、为什么这么分 | 字段与实现细节 |
| [contract.md](contract.md) | 数据结构与格式层不变量：plan / lock / state / index / verify / signatures | 流程、运维、端点 |
| [features.md](features.md) | 功能台账：一行一条，事实 / 状态 / 证据 | 机制（看证据指向的代码） |

## 每篇都要带的头

```yaml
---
kind: ledger            # contract / decision / ledger / concept / pointer
summary: 一行说清它管什么
verified: 2026-11-11    # 最后一次对着代码核过的日期，不是最后修改日期
decay: 60               # 多少天后算过期；不写默认 180
review: 任何行为变更的提交   # 什么事件会让它失效（给人读）
---
```

分类、保质期、删文档的连带动作，以及「读完文档先做体检」的流程，写在仓库根的 [AGENTS.md](../AGENTS.md)。`snapshot` / `research` 类不许进 `docs/`：结论并进台账后删原文，草稿放 `tmp/`。

## 自动检查

```bash
pnpm docs:audit
```

查四件事，任一失败退出 1，CI 的 `verify` job 里也跑：

1. 每篇有没有 `kind` + `verified`，`kind` 是否合法；
2. 有没有过期（`verified + decay`，或显式 `expires`）；
3. 正文里的相对链接能不能打开；
4. 有没有占位标记（`[待更新]`、`[待消费]`、`TBD`、`待补充`），以及 `docs/README` 没指向的孤儿文档（warning）。


## 台账规则

- **编号前缀是域，不复用**；补项往后追加，不改号。功能被删不删行，状态改 `[na]` 并写清何时、为何删。
- **状态五档**：`[done]` 代码在、主路径有测试或实测；`[part]` 有但功能上有明确缺口；`[parked]` 代码在但已冻结，不再推进也不再维护；`[todo]` 没有；`[na]` 不属于 PackHub 或已移除。
- **「事实」写能观察到的行为**，不写「支持 XX」。
- **证据是仓库内能打开的名字**：文件路径、符号、测试名。写不出证据就不写这条。

## 维护

- 改行为 → 同一次提交里改台账对应行。
- 加能力 → 先加台账行（新编号），再补测试；测试名就是证据。
- 删能力 → 先删测试，再把台账行改 `[na]` 并注明替代物。
- 不抄可变量：**凡一次提交就会变的计数都不写**——测试文件数、用例数、命令数、路由数、检查项数、行号、提交号。要指数量就写去哪读（`pnpm check` 的输出、`packhub --help`、对应源文件里的常量）。
- 不写「待更新」「待消费」：做不到就不写这条，做得到就写准。需要跟随的用指针。
- 不写散文式的实现说明：没人维护的机制说明，比多读两遍代码更贵。要展开就写进代码注释或测试名。
